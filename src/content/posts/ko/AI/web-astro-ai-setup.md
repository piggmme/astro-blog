# AI 에이전트가 팀 규칙대로 일하게 만들기

## 2인 팀의 Claude Code 세팅기

저희 팀은 프론트엔드 개발자 두 명이 Astro 기반 웹 클라이언트를 만들고 있습니다.
2026년 3월부터 Claude Code 를 본격적으로 쓰기 시작했고, 10월에는 저장소 커밋의 **90%** 가 Claude 와 함께 작성됐습니다.

AI 가 코드를 많이 쓰게 되면 새로운 문제가 생깁니다.
**AI 가 쓴 코드가 팀 규칙을 지키는가?** 다국어 파일 하나를 빠뜨려 화면 전체가 깨지거나, 타입 에러를 "기존 에러라 무관합니다" 하고 넘어가거나, main 브랜치에 바로 커밋하는 일이 실제로 있었습니다.

이 글은 그런 일을 겪으며 **AI 가 팀 규칙대로 일하도록** 만들어 온 세팅을 정리한 기록입니다.

## 전체 구조: 원본은 하나, 나머지는 따라간다

저희는 Claude Code 를 주로 쓰지만 GitHub Copilot 과 Codex 도 함께 씁니다.
도구마다 규칙 파일을 따로 관리하면 금방 서로 달라지기 때문에, **규칙의 원본은 `.claude/` 한 곳** 에만 두기로 했습니다.

```
web-astro/
├── CLAUDE.md                ← 목차. 어떤 일에 어떤 문서 · 에이전트 · 스킬을 쓸지 안내
├── .claude/                 ← 규칙의 원본 (single source of truth)
│   ├── docs/        9개     ← 상세 규칙: 코딩 컨벤션, 커밋 규칙, 상태관리 가이드 …
│   ├── agents/      5개     ← 서브에이전트: bug-fixer, i18n-syncer …
│   └── skills/     10개     ← 절차형 작업: issue-pair, api-sync, spec-sync …
├── .github/                 ← Copilot 용 사본 (sync-to-copilot 스킬로 복사)
├── AGENTS.md, .codex/       ← Codex 용 진입점 ("CLAUDE.md 와 .claude/ 를 읽어라")
└── scripts/pre-push.sh      ← 사람 · AI 모두에게 걸리는 마지막 관문
```

아래에서 하나씩 살펴보겠습니다.

## 1. CLAUDE.md 는 목차로만 쓴다

처음 CLAUDE.md 는 168줄이었습니다. 아키텍처 설명, 코딩 규칙, 커밋 규칙이 한 파일에 다 들어 있었죠.
문제는 **CLAUDE.md 는 매 대화마다 통째로 읽힌다** 는 점입니다. 지금 하는 작업과 상관없는 규칙까지 매번 컨텍스트를 차지하고, 정작 중요한 규칙이 묻힙니다.

그래서 CLAUDE.md 를 **47줄짜리 목차** 로 줄이고, 상세 규칙은 `.claude/docs/` 로 옮겼습니다.
CLAUDE.md 에는 "이런 요청이 오면 이걸 봐라" 만 남깁니다.

```md
## 어떤 요청이 들어오면 무엇을 참고하나

- 신규 컴포넌트 작성 → `.spec.md` 먼저 작성 후 SDD 절차로 구현
- `src/api/` 백엔드 요청 함수 작성/추가 → `api-request-conventions.md`
- 다국어 추가/수정 (4 로케일) ⚠️ → agent `i18n-syncer` 필수 (ko 만 건드리지 말 것)
- 버그 제보 (진단 선행) → agent `bug-fixer`
- 커밋 직전 → `commit-rules.md`
```

AI 는 목차를 보고 필요한 문서만 골라 읽습니다. 사람에게도 "이 프로젝트에서 무슨 일을 할 때 무엇을 봐야 하는지" 한눈에 보이는 지도가 됐습니다.

## 2. 규칙에는 "왜" 를 날짜와 함께 남긴다

규칙만 적어 두면, 시간이 지나 **이 규칙이 왜 있는지** 아무도 모르게 됩니다. 사람도 그렇고 AI 도 그렇습니다.
이유를 모르는 규칙은 상황이 조금만 달라도 지켜지지 않거나, 반대로 맞지 않는 상황에까지 기계적으로 적용됩니다.

그래서 규칙을 추가할 때마다 **어떤 사고가 있었는지를 날짜와 함께** 적습니다.

> **타입 에러는 게이트다** — 통과 기준은 변경 파일 에러 0 그리고 저장소 총계 증가 0.
> - 왜 이 항목이 추가됐나 (2026-09-23): 메인이 타입 에러를 보고만 하고 넘어갔다 — `astro check` 12건을 "기존 에러라 무관" 으로 정리하고 그대로 커밋 · PR 로 갔다. 보고는 통과 사유가 아니다.

> **커밋 직전 현재 브랜치 확인 필수** — main 에서는 커밋하지 않고 작업 브랜치를 먼저 판다
> - (2026-09-28 main 직접 커밋 사고 후 추가)

이 원칙을 지키려고 CLAUDE.md 에 이런 규칙도 넣었습니다.

> 행동지침 추가 요청 시 → 추가 전에 반드시 사용자에게 이유를 물어보고, 해당 이유를 문서에 기록

"이 규칙 추가해줘" 라고 하면 AI 가 먼저 "왜 추가하나요?" 를 묻습니다. 귀찮을 것 같지만, 덕분에 모든 규칙에 히스토리가 남습니다.

## 3. 메인 세션은 지휘만, 반복 작업은 서브에이전트에게

AI 와 오래 대화하면 앞에서 말한 규칙을 점점 놓칩니다. 컨텍스트가 길어질수록 맥락이 흐려지는 **Context Rot** 입니다.
그래서 메인 세션은 **사용자와 대화하고, 결정하고, 결과를 합치는 일** 만 하고, 반복적이거나 탐색이 많은 일은 서브에이전트에게 맡깁니다.
서브에이전트는 깨끗한 컨텍스트에서 시작해 자기 일만 하고 결론만 돌려줍니다.

| 에이전트 | 하는 일 | 쓸 수 있는 도구 |
| --- | --- | --- |
| `bug-fixer` | 버그 원인을 분석하고, **승인을 받은 뒤에만** 수정 | Read, Edit, Grep, Glob, Bash |
| `i18n-syncer` | ko · en · ja · zh 4개 로케일을 동시에 수정 | Read, Edit, Grep, Glob |
| `style-enforcer` | PR 직전 컨벤션 정리 + eslint 통과 (동작 변경 금지) | Read, Edit, Grep, Glob, Bash |
| `legacy-refactor-scout` | 레거시 파일 진단 → 단계별 리팩토링 계획 | Read, Edit, Grep, Glob, Bash |
| `backend-types-refresher` | 백엔드 스펙에서 타입 재생성 + 영향 범위 보고 | Read, Grep, Glob, Bash |

에이전트마다 **쓸 수 있는 도구를 일부러 제한** 했습니다. 번역만 하는 `i18n-syncer` 는 셸 명령을 쓸 수 없고, 타입을 다시 뽑기만 하는 `backend-types-refresher` 는 파일을 직접 고칠 수 없습니다.

가장 효과가 컸던 건 `bug-fixer` 의 첫 번째 규칙입니다.

> 진단 리포트 없이 Edit/Write 금지. 첫 응답은 반드시 원인 분석 + 해결 방안 보고

AI 는 버그를 보면 바로 고치고 싶어 합니다. 그러다 보면 원인이 아니라 증상을 가리는 수정(try/catch 로 에러 삼키기 같은)이 나옵니다.
진단을 먼저 보고하게 하니, **사람이 원인을 이해한 뒤에 수정이 들어갑니다.**

`i18n-syncer` 도 사고에서 나왔습니다. 저희 프로젝트는 다국어 키가 한 로케일이라도 빠지면 화면 전체가 렌더되지 않습니다. 한국어 파일만 고치고 끝내는 실수를 막으려고, 다국어 작업은 무조건 이 에이전트에게 맡기도록 했습니다.

## 4. 절차가 정해진 작업은 스킬로

에이전트가 "누가 할지" 라면, 스킬은 "어떻게 할지" 입니다.
여러 단계를 정해진 순서로 밟아야 하는 작업은 스킬로 만들어 두고, 트리거 문장이나 `/스킬이름` 으로 부릅니다.

- **`issue-pair`** — "이슈 만들어줘" 하면 Jira 이슈와 GitHub 이슈를 짝으로 만들고 서로 링크합니다. 브랜치 이름과 커밋 메시지에도 두 번호가 함께 들어갑니다.
- **`legacy-ts-migration`** — 레거시 jsx 를 tsx 로 옮기는 절차입니다. Redux 를 유지할지 걷어낼지 먼저 판단하고, 실제 사용처를 교체한 뒤 레거시 파일은 바로 지우지 않고 `@deprecated` 로 남깁니다.
- **`api-sync`** — 백엔드 v3 API 스펙을 다시 받아 요청 함수와 store 까지 한 번에 갱신하고, 영향받는 화면을 보고합니다. 스펙이 바뀌지 않았으면 아무것도 하지 않습니다.
- **`spec-sync`** — 컴포넌트의 `.spec.md` 가 바뀌면 같은 폴더의 컴포넌트 · 테스트 · 스토리를 함께 고칩니다.

어떤 작업을 에이전트로 둘지 스킬로 둘지는 지금도 고민입니다.
처음엔 다국어 · 컨벤션 정리를 에이전트에서 스킬로 옮겼다가, 다시 에이전트로 되돌리기도 했습니다. 지금 기준은 **"깨끗한 컨텍스트에서 따로 일해야 하면 에이전트, 메인 세션이 따라 하기만 하면 되는 절차면 스킬"** 입니다.

## 5. 코드보다 spec 이 먼저

컴포넌트마다 `.spec.md` 를 둡니다. 저장소에 135개가 있습니다.
spec 에는 Props, 상태와 동작, 접근성 같은 **이 컴포넌트가 지켜야 할 약속** 이 적혀 있고, 규칙은 하나입니다.

> `.spec.md` 가 있는 파일을 고칠 때는 spec 먼저 → 코드 → 같은 커밋

AI 에게 "이 버튼 동작 바꿔줘" 라고 하면, 코드보다 spec 을 먼저 고치고 그 spec 에 맞춰 코드 · 테스트 · 스토리를 고칩니다.
spec 이 **AI 와 사람이 함께 보는 설계서** 가 되는 겁니다. 리뷰할 때도 spec diff 를 먼저 보면 의도가 바로 보입니다.

## 6. 사람이 꼭 해야 하는 일은 남겨 둔다

AI 에게 맡기지 않기로 한 일도 분명히 정했습니다.

- **커밋은 사람이 확인한 뒤에만.** AI 는 변경 요약을 먼저 보여 주고 "이대로 커밋할까요?" 를 묻습니다. 사람이 화면에서 동작을 확인하기 전에는 커밋하지 않습니다.
- **푸시는 절대 AI 가 하지 않습니다.** 외부에 나가는 일은 사람이 직접 합니다.
- **커밋 직전에 브랜치를 확인합니다.** main 이면 커밋하지 않고 작업 브랜치부터 만듭니다.
- **작업 완료 보고에는 "눈으로 확인할 곳" 을 꼭 넣습니다.** 프론트엔드는 테스트가 통과해도 화면이 깨질 수 있습니다. 바뀐 파일 목록만 받으면 사람이 "이게 어느 화면이지?" 를 다시 추적해야 하니, 이미 코드를 읽은 AI 가 확인할 화면을 정리해 줍니다.

그리고 사람과 AI 모두에게 걸리는 **마지막 관문** 으로 git pre-push 훅을 둡니다.

```sh
# scripts/pre-push.sh (요약)
node scripts/check-i18n.mjs   # ko 기준으로 en · ja · zh 에 빠진 키가 있으면 push 차단
# 태그 push 면 package.json 버전과 태그가 같은지 확인
pnpm eslint
```

규칙 문서는 AI 가 읽고 따르는 것이지만, 훅은 **읽든 말든 막습니다.** 화면 전체가 깨지는 다국어 누락 같은 사고는 문서가 아니라 훅으로 막는 게 맞다고 판단했습니다.

## 7. 다른 AI 도구와 함께 쓰기

GitHub Copilot 과 Codex 를 연결하는 방식은 서로 다르게 가져갔습니다.

- **Copilot — 복사.** Copilot 용 문서는 그 자체로 완결되도록 만든다는 원칙에 따라, `sync-to-copilot` 스킬로 `.claude/` 의 문서 · 에이전트 · 스킬을 `.github/` 로 복사합니다. 위험한 명령(`rm -rf`, `git push --force` 등)을 실행하기 전에 확인을 받는 훅도 Copilot 쪽에 따로 두었습니다.
- **Codex — 가리키기.** `AGENTS.md` 와 `.codex/` 에는 "`CLAUDE.md` 와 `.claude/` 를 먼저 읽어라" 만 적고, 내용은 복사하지 않습니다.

직접 운영해 보니 **복사는 결국 어긋납니다.** 이 글을 쓰면서 확인해 보니, 다국어 스킬은 원본이 93줄인데 Copilot 사본은 77줄이었습니다. 원본에 최근 추가한 중복 키 검사 규칙이 사본에는 빠져 있었죠.
가리키는 방식이 가능하다면 그쪽이 낫고, 복사가 필요하다면 동기화를 사람이 기억하는 일로 두지 말고 자동화해야 한다는 숙제가 남았습니다.

## 마치며

세팅을 돌아보면 결국 하나의 원칙으로 모입니다.

> **AI 에게 규칙뿐 아니라 규칙이 왜 생겼는지 알려준다.**

규칙만 주면 AI 는 비슷하지만 다른 상황에서 그 규칙을 놓칩니다. 사고와 이유를 함께 주면, 처음 보는 상황에서도 규칙의 의도에 맞게 판단할 가능성이 커집니다.
그리고 그 "왜" 를 쌓아 두는 일은 AI 만을 위한 게 아니었습니다. 몇 달 뒤 저희 팀이 같은 실수를 반복하지 않게 해 주는 기록이기도 했습니다.
